# RK3576 Ubuntu 24.04 全硬件能力适配技术方案

## 1. 文档目标

本文给出将当前 RK3576 SDK 的 Debian/Buildroot 根文件系统扩展为 Ubuntu 24.04 LTS arm64，并保证以下能力达到可交付状态的实施方案：

- Mali GPU 3D 加速及显示合成
- MPP/RGA 视频硬件解码、编码和图像处理
- MIPI-CSI/USB 摄像头、RKISP 和 RKAIQ 3A
- RKNPU2 推理和 RK3576 模型运行
- HDMI/DP/DSI 显示、音频、网络、USB、存储等基础外设
- 可重复构建、可烧录、可升级、可回归测试

本文依据当前仓库实际结构制定，目标板配置以 `rk3576-omniego` 为当前基线。若最终硬件不是该板型，摄像头、电源、显示和 GPIO 部分必须按实际原理图重新核对。

## 2. 结论与总体路线

采用以下原则：

1. 保留 SDK 自带的 U-Boot、Rockchip Linux 6.1 内核、设备树、固件分区和烧录工具。
2. 只将 Debian Bookworm 用户空间替换为 Ubuntu 24.04 LTS arm64 用户空间。
3. Rockchip 硬件能力使用本 SDK 中与内核匹配的 BSP 驱动和用户态组件，不使用 Ubuntu generic 内核。
4. 能从源码构建的组件全部针对 Ubuntu 24.04 重编并生成 `.deb`；只有无法获得源码的 Mali/RKNPU 闭源库允许复用供应商二进制。
5. Debian 原镜像作为 Golden Reference，Ubuntu 每项功能必须与其做功能和性能对照。

不建议直接烧录 Ubuntu 官方 Server 镜像。官方镜像的启动布局、内核、设备树和 Rockchip 多媒体栈均不匹配本 BSP。

建议第一版采用 Ubuntu 24.04 LTS Server + Weston，稳定后再增加 Xfce/GNOME。硬件栈的首选显示路径是 DRM/KMS + GBM + Wayland，X11 作为兼容项。

## 3. 为什么从厂家 Debian 切换到 Ubuntu

### 3.1 需求的本质

本项目切换 Ubuntu 的目的不是为了获得不同的 Linux 内核或更好的 RK3576 驱动。GPU、MPP/RGA、摄像头、ISP 和 NPU 能力主要由厂家 BSP 内核、设备树、固件及配套用户态库决定；把 Debian rootfs 换成 Ubuntu rootfs，不会自动改善这些硬件能力。

切换的核心价值是把产品的应用运行环境统一到 Ubuntu 24.04 LTS，从而降低上层软件适配、开发环境维护、第三方交付和后续运维成本。实施后形成的实际系统是：

```text
厂家 RK3576 启动链和 BSP 内核
              +
Ubuntu 24.04 LTS 用户空间
              +
经过 Ubuntu 适配的 Rockchip GPU/多媒体/Camera/NPU 软件栈
```

因此，本项目不是把整套厂家 BSP 替换成 Canonical 官方 RK3576 平台，也不承诺可以直接使用 Ubuntu generic 内核。厂家 Debian 仍作为硬件功能和性能的 Golden Reference。

### 3.2 对本项目的直接收益

#### 3.2.1 统一开发、编译和部署环境

如果项目的服务器、开发机、CI、Docker 基础镜像或算法团队主要使用 Ubuntu，那么目标板也使用 Ubuntu 24.04，可以减少以下差异：

- 软件包名称、默认版本和安装方式差异
- Python、C/C++、CMake、GCC 和常用开发工具版本差异
- systemd、NetworkManager、Netplan、PipeWire 等系统组件配置差异
- 开发机验证正常、部署到板端后因发行版差异重新适配的问题
- 多套安装脚本、部署文档和问题处理流程的维护成本

对于需要持续迭代应用、算法和容器的产品，这种环境统一通常比发行版本身更有价值。

#### 3.2.2 改善 AI 和应用软件生态兼容性

本项目包含 RK3576 NPU、摄像头和多媒体应用，通常还会使用 Python、OpenCV、ONNX、GStreamer、ROS、Docker 或其他第三方 SDK。许多上游厂商和开源项目优先提供 Ubuntu 的安装说明、CI 测试结果或预编译 arm64 软件包。

采用 Ubuntu 24.04 后，可能减少第三方应用层组件的源码回编和依赖排查工作，尤其适合：

- AI 推理服务和模型管理工具
- OpenCV/GStreamer 业务程序
- 容器化边缘服务
- ROS 及机器人相关组件
- 客户只提供 Ubuntu 安装包或 Ubuntu 部署手册的软件

这里的收益主要位于 NPU 运行库之上的应用层。RKNPU 内核驱动、`librknnrt` 和 RKNN 模型仍必须使用与 RK3576 BSP 匹配的版本，不能用 Ubuntu 软件源替代。

#### 3.2.3 更容易满足客户和第三方交付要求

如果最终客户的验收环境明确指定 Ubuntu，或者第三方程序只承诺支持 Ubuntu，那么继续使用厂家 Debian 会产生额外的兼容性责任：出现问题时，第三方可能首先要求在其支持的 Ubuntu 环境复现。

目标板采用 Ubuntu 后，可以统一以下交付口径：

- 系统版本和安全更新说明
- 应用安装和升级方式
- Docker/容器运行环境
- 运维命令、日志位置和故障采集方法
- 客户已有的 Ubuntu 自动化部署工具

这能降低跨团队联调和售后定位成本，但前提是项目自己承担 Rockchip BSP 用户态栈在 Ubuntu 上的验证责任。

#### 3.2.4 获得清晰的长期维护基线

Ubuntu 24.04 LTS 可以作为产品用户空间的长期固定版本，便于项目建立：

- 固定的软件仓库和离线镜像源
- 自有 Rockchip deb 仓库
- CVE 评估、补丁和升级策略
- 软件包 manifest、SBOM 和版本追踪
- 开发、测试、量产和现场环境的一致版本线

这不等于可以不经验证地执行全系统在线升级。Rockchip 图形、多媒体、Camera 和 NPU 包与 BSP 存在强耦合，仍需要包 pinning、内部发布仓库和整机回归测试。

#### 3.2.5 有利于建立产品化系统，而不是依赖厂家演示镜像

厂家 Debian 镜像首先承担板卡功能演示和参考验证作用，其中可能包含预装测试程序、调试账号、批量 hold 的软件包、非项目需要的桌面组件和不可追溯的手工修改。

本次 Ubuntu 移植会同步建立可重复生成的 rootfs、明确的软件清单、自有 deb 包、自动测试和发布流程。对项目的长期收益不只是“系统名称变成 Ubuntu”，而是形成一套由项目团队可维护、可复现和可回归的产品镜像工程。

### 3.3 不应被当作迁移理由的事项

以下说法不能作为单独立项依据：

- “Ubuntu 一定比 Debian 稳定”：稳定性取决于 BSP 匹配、配置、测试和升级控制，不取决于发行版名称。
- “切换 Ubuntu 后 GPU/NPU 性能会更高”：相同内核和厂家库下通常不会自然提升，反而可能因 ABI 或配置不匹配下降。
- “Ubuntu 可以直接解决摄像头问题”：Camera 主要取决于 sensor driver、DTS、MIPI、电源时序、RKAIQ 和 IQ 文件。
- “Ubuntu 包更多所以所有软件都能直接安装”：arm64、闭源驱动、特定 ABI 和业务版本仍可能需要自行构建。
- “Ubuntu LTS 可以直接长期在线升级”：vendor 栈升级前必须经过整机回归，不能等同于普通 PC/服务器维护方式。

### 3.4 本项目为迁移付出的代价

切换 Ubuntu 会引入明确成本：

- 重建并维护 Ubuntu rootfs 构建流程
- 重编或重新打包 Mali、MPP、RGA、GStreamer、RKAIQ 和 RKNPU2 组件
- 处理 Debian 12 与 Ubuntu 24.04 的包名、ABI 和服务配置差异
- 重新完成 GPU、硬编解码、摄像头、NPU 和基础外设回归
- 维护内部 APT 仓库、包版本、升级和回滚策略
- 后续 BSP 升级时同时维护厂家 Debian 基线与 Ubuntu 产品分支

因此，Ubuntu 不是零成本替换。移植完成后的上层生态和维护收益必须能够覆盖一次性移植成本以及后续 vendor 包维护成本。

### 3.5 项目决策条件

满足以下任意一项时，迁移 Ubuntu 具有明确价值：

1. 客户合同、招标或验收明确要求 Ubuntu 24.04。
2. 核心业务软件或第三方 SDK 只正式支持 Ubuntu。
3. 项目研发、CI、容器和运维体系均以 Ubuntu 为统一标准，Debian 已造成持续适配成本。
4. 产品需要 Ubuntu 生态中的 ROS、AI、云边协同或运维组件，并且在厂家 Debian 上维护成本明显更高。
5. 团队准备建立独立、可重复、可长期维护的产品 rootfs，不再直接以厂家演示镜像量产。

如果没有上述业务或技术约束，且厂家 Debian 已满足全部功能、应用和安全维护要求，那么保留 Debian 通常风险更低、交付更快。此时不建议仅因为团队对 Ubuntu 更熟悉就承担全硬件栈重新认证的成本。

### 3.6 本项目的建议立项表述

建议将需求表述为：

> 在保留 RK3576 厂家 BSP 启动链、Linux 6.1 内核、设备树和硬件加速能力的前提下，将产品用户空间统一为 Ubuntu 24.04 LTS arm64，满足项目上层应用、AI 软件、客户交付和长期运维环境的统一要求；同时通过 Debian Golden Reference 对照和完整回归，保证 GPU、硬编解码、摄像头及 NPU 功能和性能不发生不可接受的退化。

项目验收重点应是业务软件兼容性、可维护性以及硬件能力无退化，而不是仅检查 `/etc/os-release` 是否显示 Ubuntu。

## 4. 当前 SDK 能力盘点

### 4.1 启动和镜像链路

当前烧录流程最终消费 `rootfs.img`，rootfs 默认是 ext4。系统类型只影响根文件系统生成，不影响 Loader、U-Boot、boot.img、parameter 和升级包格式。

已有关键能力：

- RK3576 Loader/U-Boot 和 FIT boot.img
- Rockchip Linux 6.1 BSP 内核
- `rk3576-omniego.dts` 板级设备树
- ext4 rootfs 制作脚本
- firmware/update.img 打包流程
- rootfs post hooks、模块安装、fstab、udev 和日志管理

### 4.2 内核硬件能力

当前 `rockchip_linux_defconfig` 已包含：

- Rockchip DRM/KMS
- Mali Bifrost 驱动
- Rockchip MPP service、RKVDEC/RKVDEC2、RKVENC/RKVENC2
- RGA
- Rockchip CIF、RKISP、ISPP
- RKNPU 驱动及 IOMMU/电源域支持

RK3576 SoC DTS 中已有 GPU、NPU、双编码核心、解码核心、ISP、多路 CSI2 DPHY 和 IOMMU 节点。实际传感器能否工作仍取决于板级 DTS、时钟、电源、GPIO、MIPI lane 和 IQ 文件。

### 4.3 用户态组件

仓库已有以下源码或预编译包：

| 子系统 | 当前组件 | Ubuntu 处理策略 |
| --- | --- | --- |
| GPU | `external/libmali`，RK3576 映射为 Bifrost G52 g24p0 | 先验证供应商 arm64 库 ABI，再重做 Ubuntu `.deb` |
| 显示 | libdrm、Wayland、Weston、Xserver | 优先使用 Ubuntu 原生包，仅保留必要 Rockchip patch |
| 视频 | `external/mpp`、`external/gstreamer-rockchip` | 在 Ubuntu 24.04 原生 GStreamer 上重编 |
| 图像 | `external/linux-rga` | 从源码重编 `.deb` |
| 摄像头 | `external/camera_engine_rkaiq`、rkisp 包 | 按 RK3576 编译，安装传感器 IQ 文件和 systemd 服务 |
| NPU | `external/rknpu2` runtime/examples | 复用匹配驱动的 runtime，重编 demo 并生成 `.deb` |
| 无线 | `rkwifibt` 和 firmware | 复用固件，调整 Ubuntu NetworkManager/BlueZ 服务 |

当前 Debian 包主要按 Debian 12 构建。Ubuntu 24.04 的 glibc 通常能满足较低版本符号要求，但包名、依赖名和 GStreamer/Wayland ABI 不能仅凭 `dpkg --force` 判断兼容，必须通过重新构建和运行测试确认。

## 5. 版本与制品基线

### 5.1 固定版本

- 发行版：Ubuntu 24.04 LTS arm64
- 用户空间：从 Ubuntu ports 仓库使用 `debootstrap --foreign` 创建
- 内核：本 SDK Rockchip Linux 6.1，禁止第一阶段升级到 Ubuntu generic/mainline
- U-Boot/DTB：保持当前已在 Debian/Buildroot 上验证过的提交
- libc：Ubuntu 24.04 仓库版本
- init：systemd
- 网络：NetworkManager
- 音频：PipeWire + ALSA
- 图形：DRM/KMS + GBM + Wayland/Weston
- 软件包格式：deb，建立项目自己的 APT 仓库或离线 package pool

### 5.2 可追溯性

每个镜像必须写入：

- SDK Git commit/submodule commit
- kernel、U-Boot、DTB commit
- Ubuntu suite、snapshot/mirror 和构建日期
- Rockchip 用户态包版本及源码 commit
- 板型、硬件版本和摄像头模组型号
- SHA256 清单和构建日志

镜像版本禁止只使用 `latest`。建议格式：

`rk3576-omniego-ubuntu2404-YYYYMMDD-buildNN`

## 6. 构建系统改造

### 6.1 新增目录

建议新增而不是改写 `debian/`：

```text
ubuntu/
├── README.md
├── mk-base-ubuntu.sh
├── mk-rootfs-noble.sh
├── mk-image.sh
├── manifests/
│   ├── base.packages
│   ├── desktop.packages
│   └── rockchip.packages
├── overlay/
├── overlay-firmware/
├── packages/arm64/
└── tests/
```

### 6.2 SDK 入口

新增：

- `device/rockchip/common/configs/Config.in.ubuntu`
- `device/rockchip/common/scripts/check-ubuntu.sh`
- `build_ubuntu()` rootfs 构建函数
- `RK_UBUNTU_VERSION=noble`
- `RK_UBUNTU_ARCH=arm64`
- `RK_ROOTFS_SYSTEM_UBUNTU`
- `./build.sh ubuntu` 命令

构建完成后必须输出：

```text
output/<board>/ubuntu/images/rootfs.ext4
output/firmware/rootfs.img
```

后续 `./build.sh firmware` 和 update.img 打包继续复用现有流程。

### 6.3 rootfs 生成

推荐步骤：

1. `debootstrap --arch=arm64 --foreign noble` 创建 stage 1。
2. 注入 `qemu-aarch64-static`，在 chroot 内执行 stage 2。
3. 安装基础包、systemd、NetworkManager、SSH、ALSA、PipeWire 和诊断工具。
4. 安装 SDK 构建的 kernel modules、firmware、Rockchip deb 包。
5. 执行现有 post-rootfs hooks，修正 fstab、hostname、udev、ldconfig。
6. 清除 machine-id、SSH host keys、APT cache 和临时文件。
7. 使用 `mkfs.ext4 -d` 生成 rootfs.ext4。
8. 生成包清单、SHA256 和 SBOM。

构建应支持离线缓存，避免每次使用变化中的在线仓库产生不可复现镜像。

## 7. 软件包兼容与重编策略

### 7.1 分层原则

按以下顺序处理软件：

1. Ubuntu 官方包：systemd、libdrm、Mesa 基础组件、Wayland、Weston、GStreamer、PipeWire、V4L2 工具。
2. SDK 开源包：MPP、RGA、gstreamer-rockchip、RKAIQ 等，在 noble sysroot 中重编。
3. 供应商闭源包：Mali DDK、RKNPU runtime 等，保留原始二进制，仅重做控制文件和安装脚本。
4. 禁止用 Debian 包批量覆盖 Ubuntu 的 libdrm、GStreamer、Wayland、Xserver 核心包。这会导致系统升级后 ABI 混杂。

### 7.2 包质量要求

每个自有 deb 包必须：

- 使用唯一版本后缀，例如 `+rk3576ubuntu1`
- 声明准确 Depends/Conflicts/Replaces
- 不在 postinst 中访问网络
- 不硬编码 Debian 目录和服务路径
- 支持 `apt install`、`apt upgrade`、`apt remove`
- 安装后通过 `ldd`、`dpkg -V` 和基本 smoke test

构建时执行 `dpkg-shlibdeps` 或等效符号依赖扫描，并用 `readelf --version-info` 检查 GLIBC/GLIBCXX 需求。

## 8. GPU 与显示适配

### 8.1 实施路径

1. 使用现有 BSP Mali Bifrost 内核驱动，确认 `/dev/mali0` 创建。
2. 使用 RK3576 对应的 G52 g24p0 用户态库，不安装其他芯片的 G31/G610 包。
3. 选择与产品一致的 winsys：优先 `wayland-gbm`；需要 X11 时再提供独立 flavour，避免多个 libMali 同时安装。
4. 保持 Ubuntu 的 libdrm/Wayland 主包，Mali 包只提供 EGL/GLES/OpenCL 和必要 ICD/alternatives 文件。
5. 配置 udev group 权限，图形进程不允许依赖 root 身份。
6. 校验 DRM connector、plane、VOP、HDMI/DSI、EDID、热插拔和多分辨率。

### 8.2 验收标准

- `dmesg` 无 Mali probe、IOMMU、page fault、GPU reset 错误
- `eglinfo` 显示硬件 renderer，不允许 llvmpipe/softpipe
- `glmark2-es2-wayland` 连续运行 8 小时无崩溃、花屏和 GPU reset
- Weston 启动、HDMI 热插拔、1080p/4K 切换正常
- suspend/resume 后 GPU 和显示可恢复
- 普通用户可访问 `/dev/dri/renderD*` 和 `/dev/mali0`
- 性能相对 Debian Golden Reference 下降不超过 10%，否则必须说明原因

### 8.3 主要风险

- Mali 闭源库与内核 DDK 版本必须成套，不能任意升级其中一侧。
- Ubuntu Mesa 的 EGL alternatives/GLVND 可能与 libMali 文件冲突。
- X11 和 Wayland flavour 混装容易产生 EGL/GBM 链接错误。

## 9. 视频硬编解码与 RGA

### 9.1 实施路径

1. 保持 BSP 的 RKVDEC/RKVENC/MPP 内核驱动。
2. 在 Ubuntu noble sysroot 中重编 `external/mpp`，生成 runtime/dev/demo deb。
3. 重编 `external/linux-rga`，确认 dma-buf、IOMMU 和 cache flush 路径。
4. 使用 Ubuntu 原生 GStreamer 版本重编 `external/gstreamer-rockchip` 插件。
5. 不直接覆盖 Ubuntu 全套 GStreamer 核心库；只维护 Rockchip 插件和确有必要的 patch。
6. 用 `gst-inspect-1.0` 检查插件加载和依赖，不允许出现 undefined symbol。

### 9.2 测试矩阵

至少准备固定校验和的媒体样本：

| 类型 | 最低覆盖 |
| --- | --- |
| 解码 | H.264、H.265/HEVC、VP9、AV1、JPEG |
| 编码 | H.264、H.265、JPEG，以硬件能力为准 |
| 分辨率 | 720p、1080p、4K，最高规格按芯片和产品要求补充 |
| 色彩 | NV12/NV21、YUV420、RGB；8-bit/10-bit 按能力覆盖 |
| 输入 | 文件、摄像头、网络流 |
| 输出 | DRM/KMS 显示、文件、appsink |

### 9.3 验收标准

- MPP demo 能正确解码/编码，输出帧数、CRC 或 MD5 符合预期
- GStreamer 管线明确加载 Rockchip 硬件插件
- 4K 连续播放 24 小时无泄漏、卡死、花屏和内核错误
- CPU 占用和帧率与 Debian 对照，确认没有回退到软件解码
- 解码、RGA、显示零拷贝路径可工作；通过 dma-buf 日志/trace 验证
- 多路并发数量按产品需求定义并稳定运行 8 小时
- 编解码压力下温控、降频和内存占用可接受

## 10. 摄像头、ISP 和 RKAIQ

摄像头是本项目风险最高的部分。Ubuntu 本身不是主要变量，真正决定稳定性的是板级 DTS、sensor driver、MIPI 时序、IQ 文件和 RKAIQ 版本是否匹配。

### 10.1 开始前必须冻结的信息

- 每一路 sensor 型号和 silicon revision
- 模组厂商、镜头、facing、module index
- MIPI lane 数、lane mapping、clock frequency
- I2C bus/address
- reset/pwdn GPIO 和有效电平
- AVDD/DOVDD/DVDD 电源和上电时序
- MCLK 频率
- 输出模式、分辨率、帧率、HDR 模式
- 对应 IQ XML/JSON 文件版本

没有实际传感器型号和模组信息，不能承诺“摄像头全部稳定”。

### 10.2 实施路径

1. 先在现有 Debian 镜像记录工作基线：media graph、v4l2 format、帧率、曝光、白平衡和画质。
2. 核对 `rk3576-omniego.dts` 是否真正包含产品使用的 sensor endpoint；SoC 级 CSI/ISP 节点存在不等于板级摄像头已经配置。
3. 保持 sensor、CSI2 DPHY、CIF、ISP 驱动与当前内核版本一致。
4. 为 RK3576 重编 `camera_engine_rkaiq`，生成独立 deb 和 systemd service。
5. IQ 文件按 sensor + module + lens 精确匹配，并纳入版本控制/制品清单。
6. 设置 media node 权限，避免依赖 root。
7. 验证 V4L2 直出、ISP 处理、GStreamer 预览、编码和 NPU 联动。

### 10.3 验收标准

- `media-ctl -p` 链路完整，所有 entity/link/format 正确
- `v4l2-compliance` 关键测试通过，已知例外形成白名单
- 每个规定 mode 可连续采集，帧率误差小于 1%
- 连续采集 24 小时无 CSI error、frame loss 累积、IOMMU fault
- 自动曝光、自动白平衡、自动对焦（若支持）在规定场景稳定
- HDR/多摄同步按产品需求单独验收
- 摄像头拔插仅适用于硬件支持热插拔的接口；MIPI 模组默认不做带电拔插承诺
- suspend/resume、服务重启和异常进程退出后能够恢复

## 11. NPU 适配

### 11.1 版本配对

RKNPU 内核驱动、librknnrt、模型编译工具链版本必须建立兼容矩阵。模型必须以 `target_platform=rk3576` 转换，不能用其他 RK 平台的 RKNN 文件替代正式验证。

### 11.2 实施路径

1. 确认 `/dev/dri/renderD*` 或供应商 NPU 设备节点及 rknpu probe 正常。
2. 从 SDK 的 `external/rknpu2` 选择 RK3576 Linux arm64 runtime。
3. 将 runtime、headers、examples 分成独立 deb；配置动态库缓存和 udev 权限。
4. 重编 mobilenet、benchmark、dynamic shape、zero-copy 等示例。
5. 固定 RKNN Toolkit2 版本，在 x86_64 CI/构建机完成模型转换；目标板只负责推理。
6. 对实际业务模型验证算子支持、精度、内存、延迟和热稳定性。

### 11.3 验收标准

- 官方/仓库 Mobilenet 示例输出 Top-1 结果正确
- 相同模型连续运行 24 小时，无驱动 reset、IOMMU fault 和内存增长
- 单模型和多 context 并发均覆盖
- zero-copy/RGA + NPU 路径可工作
- 输出结果相对转换前模型满足业务定义的精度阈值
- P50/P95 延迟、FPS、DDR 占用、温度和功耗有记录
- 性能相对 Debian Golden Reference 下降不超过 10%
- 每个交付模型保存原始模型 SHA256、转换参数、Toolkit2 版本和 RKNN SHA256

## 12. 基础系统集成

Ubuntu rootfs 还必须完成以下工作，否则硬件单项通过仍不能称为稳定镜像：

- 安装与当前 kernel release 精确匹配的 `/lib/modules/<release>`
- 执行 depmod，验证自动加载和 initramfs/FIT 路径
- 安装 `/lib/firmware/rockchip` 及 Wi-Fi/Bluetooth 固件
- NetworkManager、wpa_supplicant、BlueZ 服务冲突清理
- ALSA UCM/拓扑、PipeWire session manager 配置
- udev rules：DRM、Mali、RGA、MPP、camera、NPU 权限
- systemd 服务依赖和启动顺序
- journald 日志上限，防止 rootfs 被写满
- rootfs 首次启动扩容
- 时间同步、locale、hostname 和 SSH host key 首启生成
- apt 包 hold 仅限确有冲突的 Rockchip 包，禁止 `apt-mark hold` 全系统

## 13. 验证体系

### 13.1 三层测试

1. 构建测试：镜像可重复生成，包依赖闭合，所有 ELF 无缺失动态库。
2. 板上自动测试：启动、设备节点、服务、GPU、MPP、RGA、camera、NPU smoke test。
3. 稳定性测试：长时间并发、重启、断电、温度、内存和存储压力。

### 13.2 每次构建的自动门禁

- 启动 10 次成功率 100%
- `systemctl --failed` 为空或仅包含批准的白名单
- `dmesg` 不出现 panic、oops、IOMMU fault、GPU/NPU reset、hung task
- GPU renderer 不得为软件渲染
- MPP 解码 CRC/MD5 正确
- 摄像头规定 mode 能抓取固定帧数
- NPU 模型输出正确
- 网络、USB、存储、音频 smoke test 通过

### 13.3 发布前稳定性门禁

- 冷启动/热启动各 100 次
- 主业务场景连续运行 72 小时
- GPU、视频、camera、NPU 四项并发压力至少 24 小时
- 断电恢复 50 次，文件系统无损坏
- 温度高低边界和 thermal throttling 测试
- suspend/resume 100 次（产品若使用该功能）
- rootfs 空间、内存、句柄、DMA buffer 无持续增长
- Debian 与 Ubuntu 对照性能报告完成

“稳定”应以以上可量化门禁定义，不能只以功能演示成功定义。

## 14. 故障证据采集

镜像内预装或提供诊断脚本，至少采集：

```text
uname -a
cat /etc/os-release
cat /proc/cmdline
dmesg
journalctl -b
lsmod
systemctl --failed
modetest -c -p
eglinfo
media-ctl -p
v4l2-ctl --all
gst-inspect-1.0
devfreq/thermal/debugfs 状态
已安装 Rockchip 包及版本
```

GPU、MPP、ISP、NPU 问题必须同时保存用户态日志和内核日志。遇到 IOMMU fault 时禁止只重启服务掩盖问题。

为了缩短周期，建议并行安排：

## 17. 风险清单与规避措施

| 风险 | 影响 | 规避措施 |
| --- | --- | --- |
| Mali DDK 与内核驱动不配套 | GPU crash/无法启动 | 锁定 SDK 成套版本，不单边升级 |
| Debian 包覆盖 Ubuntu 核心库 | apt 冲突、运行崩溃 | noble sysroot 重编，仅保留必要 vendor 包 |
| GStreamer ABI 变化 | 插件加载失败 | 基于 Ubuntu 原生 headers 重编插件 |
| RKNPU runtime/driver/toolkit 不配套 | 模型加载失败或结果错误 | 建立三者版本矩阵和模型制品记录 |
| sensor/IQ 信息不完整 | 相机无图、画质差 | 开工前冻结模组和 IQ 清单，先验证 Debian 基线 |
| Ubuntu 自动升级 vendor 栈 | 现场回归 | 自有 APT 仓库、包 pinning、版本化升级策略 |
| 只做单项测试 | 并发时 DMA/带宽/温控故障 | GPU+视频+camera+NPU 并发压力测试 |
| 板型 DTS 与实际硬件不一致 | 外设不工作 | 以原理图和量产硬件审查 DTS |

## 19. 项目启动前的硬性输入

实施前必须确认以下内容：

- 最终板型是 `rk3576-omniego`、`mlk-rk03` 还是其他自研板
- PCB revision、内存容量和存储介质
- 全部摄像头 sensor/模组/IQ 文件
- 显示接口、目标分辨率和桌面环境要求
- 视频格式、最大分辨率、帧率及并发路数
- NPU 业务模型、Toolkit2 版本、性能和精度指标
- 是否要求 X11、Wayland，还是两者都要
- 是否要求 Secure Boot、dm-verity、OTA/A-B 分区
- 量产允许的启动时间、温度、功耗和稳定性指标

这些输入未冻结前可以完成 Ubuntu 基础镜像，但不能对 GPU、硬解码、摄像头和 NPU 的最终稳定性作封版承诺。

## 20. 推荐执行顺序

第一周优先完成 P0～P3，交付能稳定启动且 GPU 正常的 Ubuntu 镜像；第二周完成 MPP/RGA/GStreamer 和单路摄像头；第三周完成全部摄像头、NPU 与业务链路；最后至少保留一周做并发和 72 小时测试。Camera DTS/IQ 若没有 Debian 成熟基线，应最早介入，而不是放到项目后期。

首个技术里程碑应定义为：同一套 U-Boot、kernel 和 DTB 下，Debian 与 Ubuntu 可切换烧录，并且 Ubuntu 通过 GPU/MPP/camera/NPU 四项最小 smoke test。达到该里程碑后，再进入性能调优和长期稳定性阶段。
